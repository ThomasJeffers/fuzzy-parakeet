## What actually broke Experiment 4

S-CSCF sent INVITE with a **Via stack** (S-CSCF, then P-CSCF, then UE). Kamailio `tm` matches the AS-side transaction on the **top** Via branch.

The old `get_header()` returned the **last** Via. The 200 OK therefore looked like this (exactly as in your capture):

```text
Via: SIP/2.0/UDP 192.168.101.4:50306
```

Kamailio never accepted that 200, retransmitted INVITE on Timer A (0.5 / 1.5 / 3.5 / 7.5 s), then generated `408 Request Timeout`. The AS was telling the truth when it said it was resending 200. Host tcpdump of `5070 → 172.22.0.20:6060` does **not** prove `tm` matched.

That is RFC 3261 §8.2.6.2, not a mystery.

`mcptt-server.py` **1.2** now copies **all** Via and Record-Route headers, in order. Unit tests in `tests/test_sip_via.py` lock that in. Same command as before:

```bash
python3 mcptt-server.py --advertise 172.30.104.240
```

After deploy, AS logs must look like `via=3 top=...172.22.0.20:6060`, not `via=1 top=192.168.101.x`.

The current server is **good enough as a lab AS** once this works. Floor INFO, RTP mixer, Direct-AS, and IMS mode stay. Do not turn it into a production MCPTT stack while 200/ACK still fail.

## Your questions, answered directly

**Can the AS stay on the EPC+IMS VM?**  
Yes. Keep `172.30.104.240:5070`. S-CSCF already reaches it. Co-location did not cause the 408. Do not move it into Docker until 200/ACK work.

**SIPp instead of sipsak?**  
Yes for REGISTER / INVITE / ACK / BYE. sipsak is fine for OPTIONS. It is a bad UAC here: it stuffed `172.30.104.30` into Via/Contact (your PCRF `403`), and it changes source ports. This P-CSCF has `match_contact_host_port = 1`, so INVITE **must** reuse the registered Contact host:port. SIPp binds one `-i`/`-p` for the whole dialog. Use `sipp/register-then-invite.xml`.

**Waydroid instead of an emulator?**  
Not yet. Neither Waydroid nor Genymotion is an LTE modem; `srsUE` still is. Waydroid is a reasonable later Linux APK host, but it is usually Android 11/13, not your Xiaomi Android 10. For Option B / priv-app work that you will show an Android team, **Genymotion Android 10** is the closer stand-in. Start **neither** until SIPp gets INVITE `200` and the AS sees `ACK`.

**iFC now?**  
No. The other write-up was right that stock `default_ifc.xml` does not route MCPTT, and wrong if that blocks Experiment 4. You already invoked the AS with `MCPTT_AS_CHECK`. Leave iFC as a **later** experiment after 200/ACK.
